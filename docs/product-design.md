# TOMOSHIBIYORI 製品・設計仕様

「日足から、明日の判断に小さな灯を。」をコンセプトとする。将来を断定するアプリではなく、
不確実な相場に対する日々の判断材料を、根拠と注意事項を添えて提示する。

## 前提

- 個人利用のPC中心Webアプリケーションとする。
- スマートフォンは閲覧のみ対応する。
- 保有銘柄とウォッチリストは別の目的・データとして管理する。
- 分析候補はウォッチリスト内と、流動性上位の市場全体を切り替える。
- 日足の終値確定後に日次更新する。
- 予測期間は1、5、20営業日とする。
- 初期分析は機械学習を使わないルールベースとする。
- テクニカル方向は上昇、停滞、下落の3種類とする。
- ロング中心の投資検討区分は購入候補、様子見、新規購入回避とする。
- 5営業日予測を候補ランキングの標準とする。
- 市場データ取得元はAlpha VantageとJ-Quantsを交換可能にする。
- J-Quantsの初期契約はLightプランとする。
- 予測は分析情報であり、注文指示とは分離する。

## 利用者の操作

### 候補確認

1. 日次処理完了後にダッシュボードを開く。
2. 購入候補、様子見、新規購入回避を切り替える。
3. 候補銘柄の根拠の強さ、価格、基準日を確認する。
4. 銘柄を選び、日足と判断材料を確認する。
5. 1、5、20営業日の分析期間を切り替える。

### 銘柄確認

1. ウォッチリストから銘柄を選択する。
2. 1か月、3か月、6か月、1年、全期間から表示期間を選択する。
3. 必要に応じて開始日と終了日を直接指定する。
4. ローソク足、出来高、取得元、調整有無を確認する。
5. 総合判定、判定要因、分析方式の版、基準日を確認する。

### 銘柄登録

1. 日次バッチがJ-Quantsの全上場銘柄マスタをローカルDBへ同期する。
2. Web画面で4文字の証券コードを最大200件まとめて入力する。
3. 同期済みマスタへ一致するコードは、その場で正式名称付きのウォッチリストへ追加する。
4. マスタ未同期または不一致のコードだけを「確認待ち」とする。
5. 次回の日次バッチで再照合し、不一致の場合は理由付きの「登録失敗」として表示する。

### 保有銘柄

1. 同期済み銘柄マスタから証券コード、数量、平均取得単価を登録する。
2. 保有銘柄はウォッチリストへ暗黙に追加せず、独立して管理する。
3. 評価表示にはリアルタイム価格ではなく、最新の日足終値を使う。
4. 日次バッチの取得対象は、保有銘柄とウォッチリストの和集合とする。

### 銘柄削除

1. ウォッチリスト行の「削除」を選択する。
2. 証券コードと銘柄名を含む確認を表示する。
3. 確認後、`watchlist_items`と対応する登録状態だけを削除する。
4. `daily_bars`とバッチ実行履歴は削除せず、再登録時の再利用と監査に残す。
5. 削除後は画面を再読み込みし、残った先頭銘柄を選択する。

## UI/UX原則

- ヘッダーと銘柄ナビゲーションを画面へ固定せず、文書の通常フローで表示する。
- PCでは銘柄ナビゲーションを折りたたみ、チャートと判断材料へ表示幅を譲れるようにする。
- 狭い画面では銘柄ナビゲーションと詳細領域を縦に並べる。
- 判定要因は3列のカードで一覧し、画面幅に応じて2列、1列へ切り替える。
- 方向を色だけで表現せず、「上昇」「下落」と文字でも表示する。
- 上昇、停滞、下落の3判定スコアを常にまとめて表示する。
- データ基準日、取得元、調整有無、予測期間を表示する。
- 古いデータ、未取得、取得失敗を区別する。
- 未校正・未承認モデルの確率を候補一覧へ表示しない。
- ルールの判定スコアを予測確率と表現しない。
- 総合判定とともに支持要因、反対要因、停滞要因を表示する。
- 投資検討区分とテクニカル方向を混同せず、両方を表示する。
- パターン一致度、出来高倍率、ブレイク幅、窓開けを表示する。
- データ同期待ち、契約プラン対象外、アドオン未契約、評価不能を区別する。
- 利用できない確認項目は中立値にせず、判定の加点・減点から除外する。
- 期間選択は銘柄を切り替えても維持する。

## サービス構成

初期段階は運用負担を抑えるため、モジュラーモノリスとする。

```text
ブラウザ
  -> FastAPI Webアプリケーション
       -> ダッシュボード照会
       -> 日足照会
       -> チャート分析照会
       -> 予測照会
       -> PostgreSQL

Docker日次バッチ
  -> MarketDataProvider
  -> Light参照データ（TOPIX、決算予定日）同期
  -> J-Quants全上場銘柄マスタ
  -> J-Quantsバルク日足（全市場）
  -> 登録待ち証券コードの銘柄マスタ照合
  -> 正規化・品質検査
  -> 日足保存
       -> ルールベース分析
  -> 予測保存
  -> 候補ランキング
  -> Slack通知
```

画面表示中に外部市場データAPIを呼ばない。画面は保存済みデータのみ参照し、速度、
再現性、API制限、障害分離を確保する。

Webとバッチは同じDockerイメージとドメインコードを使うが、実行プロセスと環境変数を
分離する。市場データAPIキーとSlack Webhookは`batch`および手動CLI用の`app`だけへ渡し、
`web`には渡さない。

## 日次バッチの実行契約

日次バッチは常駐プロセスではなく、一回実行して終了するジョブとする。外部スケジューラーが
`docker compose run --rm batch`を起動する。

1. PostgreSQL Advisory Lockを取得する。
2. `pipeline_runs`へ`running`状態を記録する。
3. J-QuantsのTOPIXと決算予定日を同期する。
4. 全上場銘柄マスタを単一トランザクションで更新する。
5. 最後に成功した対象日の翌日から、全市場の日足バルクファイルを差分取得する。
6. 登録待ち証券コードを銘柄マスタで照合し、ウォッチリストへ昇格する。
7. 保有銘柄とウォッチリストの和集合を取得し、取得元ごとにProviderを再利用する。
8. OHLCVを検証してUPSERTする。
9. 対象銘柄を1、5、20営業日で分析し、市場全体の流動性上位銘柄を5営業日で分析する。
10. 参照データ、銘柄、市場スクリーニングの結果を実行履歴へ記録する。
11. 全体状態を`success`、`partial_failure`、`failed`のいずれかで確定する。
12. Advisory Lockを解放して終了する。

銘柄単位の認証、通信、レート上限、データ不正はその銘柄の失敗として隔離する。一部失敗時も
成功銘柄は確定し、再実行時は保存済み最終日から再開する。想定外の全体障害も実行履歴を
`failed`へ更新してから再送出する。

```text

prediction/      学習、推論、確率校正

```

### J-Quants Lightプラン

- V2 APIの`x-api-key`認証を使用する。
- 調整済みOHLCVを保存し、`is_adjusted`を真とする。
- `JQUANTS_PLAN=light`を既定とする。
- 60リクエスト/分を安全に下回るよう、リクエスト間隔を1.05秒以上に制御する。
- 初期取得範囲はバルクAPIで現在日から過去5年分とする。
- プラン年数ごとのバックフィル完了を記録し、Freeからの移行時も最初の一回だけ5年分を取得する。
- APIのページネーションへ追従する。
- 401・403、429、通信障害、データ形式不正を別のエラーとして扱う。
- TOPIX四本値と決算発表予定日を日次バッチで同期する。
- TOPIX以外の指数はLight対象外として非活性表示する。
- TDnet／適時開示はアドオン未契約として非活性表示する。

全市場の日足は分析母集団として保存するが、日足の存在を理由にウォッチリストへ自動追加しない。
登録申請は`watchlist_registrations`、有効なリストと構成銘柄は`watchlists`、
`watchlist_items`へ保存する。保有は`portfolios`、`positions`へ分離し、目的の異なる一覧を
混在させない。既定の異業種10銘柄投入は互換用の任意コマンドとして残す。

## データベース設計

- 開発環境はDocker Compose上のPostgreSQLを使用する。
- スキーマ変更はAlembicだけで適用し、Web起動時にテーブルを自動作成しない。
- 接続先は`DATABASE_URL`へ集約し、将来はAmazon RDS for PostgreSQLへ差し替える。
- 日足は`symbol`、`trade_date`、`provider`を一意キーとして冪等にUPSERTする。
- 銘柄マスタ更新は全件非活性化と最新データUPSERTを同じトランザクションで実行する。
- バルクファイルごとの状態を保存し、失敗後の再実行で正常終了済みファイルを再取得しない。
- テストは開発DBと別の一時PostgreSQLを使う。
- 旧SQLiteは一度限りの移行元として読み取り専用でマウントし、確認完了まで削除しない。

## ルールベース分析

初版は次の独立したルールを集計する。

- 短期移動平均と20日移動平均、および20日線の傾き
- 分析期間に応じた価格モメンタム
- 14日RSIによる勢いと過熱感
- 実現ボラティリティと価格帯幅による停滞判定
- 出来高増加による値動きの確認
- 完成済みチャートパターン

各ルールは方向、重み、日本語の説明を返す。エンジンは重みを集計し、上昇要因と下落要因が
拮抗する場合は停滞とする。スコアは適用されたルールの重みを正規化した値であり、統計的に
校正された確率ではない。

現在方向では直近3営業日のATR換算変動と5日平均の位置を30点で評価する。RSIの買われ過ぎ・
売られ過ぎは反転方向を直接予測せず、停滞側の警戒情報とする。パターンの保有監視期間、目標到達、
期限切れも現在方向へ加点しない。上向きパターンの勢い弱化・失敗は下落要因、下向きパターンの
勢い弱化・失敗は上昇要因へ切り替え、過去の形より直近価格を優先する。

```text
AnalysisService
  -> AnalysisEngine（共通契約）
       -> RuleBasedAnalysisEngine（現在）
            -> AnalysisRule群
       -> ModelAnalysisEngine（将来）
  -> AnalysisResult（共通出力）
```

画面と候補抽出は`AnalysisResult`だけに依存する。将来のモデル方式も同じ契約を実装し、
設定または依存性注入で切り替える。売買判断では分析方式と版を必ず記録する。

### 二層のチャート評価

パターンの形と、個別株固有の確認を分離する。

```text
TechnicalPatternDetector（価格形状）
  -> レクタングル
  -> アセンディング／ディセンディング・トライアングル
  -> ダブルトップ／ダブルボトム
  -> ヘッド＆ショルダーズ・トップ／ボトム

PatternLifecycleEvaluator（検出後の状態）
  -> 新規検討期間、保有監視期間
  -> 勢い弱化、目標到達、ブレイク失敗、期限切れ

TransitionReadinessEvaluator（転換前の進捗）
  -> 下降継続、底固め観察、転換準備、あと1条件
  -> 転換初動、上昇継続、警戒

LongOnlyDecisionPolicy（個別株向け投資検討区分）
  -> 出来高倍率
  -> ATRで標準化したブレイク幅と窓開け
  -> 最終日足のデータ鮮度
  -> 売買代金ベースの暫定流動性
  -> TOPIXトレンド、業種指数、決算予定日、適時開示の評価可否
```

転換準備度は方向スコアや確率とは別の共通出力とする。必須条件の達成数、未達の次条件、転換水準、
無効化水準、参考目標、参考リスクリワードを保持する。市場全体の日次スナップショットにも段階と
進捗を保存し、「あと1条件」を後から検索できるようにする。評価器はProtocolで分離し、将来の
統計モデルへ交換しても`AnalysisResult`とWeb APIの契約を維持する。

形の検出器は前日終値から当日終値へ水準を跨いだ日だけをイベントとして記録し、直近25営業日に
発生したイベントを返す。同じ水準の外側に留まっているだけの日を再検出しない。
`pattern_fit_score`は局所高値・安値、
回帰直線の傾き、左右対称性などの条件一致度を0〜100で表すヒューリスティックであり、
将来リターンの確率ではない。

検出後は価格形状とは分離した`PatternLifecycleEvaluator`が毎日再評価する。ブレイク後5営業日を
新規検討期間、6〜20営業日を保有監視期間、20営業日超を期限切れとする。直近最大4本が期待方向へ
0.5 ATR以上逆行した場合は勢い弱化、終値がネックラインから反対方向へ0.5 ATRを越えた場合は
ブレイク失敗とする。形成値幅の目標到達も別状態にする。閾値は固定した初期運用値であり、
日本株のウォークフォワード検証後にエンジン版を上げて変更する。

### 個別株固有の特徴量

```text
volume_ratio   = ブレイク日出来高 / 過去60営業日出来高中央値
gap_atr        = (ブレイク日始値 - 前日終値) / ブレイク直前ATR(20)
breakout_atr   = ブレイク水準から終値までの方向別距離 / ブレイク直前ATR(20)
prior_trend_score = 形成前20日内の前後5日平均騰落率 × 500（-100〜100へ制限）
liquidity_score = J-Quants日本株の過去60営業日売買代金中央値による暫定評価
```

取得履歴が60営業日に満たない場合、`volume_ratio`と`liquidity_score`は20営業日以上の
取得可能期間を使い、その事実を画面に表示する。`|gap_atr| > 1.5`はギャップ主導として
通常ブレイクと区別する。決算予定日は取得するが決算内容や適時開示本文は取得しないため、
ギャップの原因を推測しない。

売買代金の閾値はJPY前提なので、現時点ではJ-Quants日本株だけに適用する。Alpha Vantageなど
日足自体に通貨情報を持たない取得元は流動性を評価不能とし、異なる通貨を同じ閾値で比較しない。

最新日足が現在日から7暦日を超えて古い場合、上向き条件を満たしても購入候補にはせず、
更新後の再確認を求める。下降パターンの新規購入回避は保守的な警戒情報として維持する。

TOPIXはLightの四本値から20営業日騰落率を算出する。決算予定日は分析期間内にある場合、
購入候補を「様子見」へ抑制する。同期前は`pending_data`、Light対象外の業種指数は
`plan_unavailable`、TDnetアドオン未契約は`addon_required`とし、0点として加算しない。
将来はベンチマーク日足からβと超過リターンを計算し、業種指数と適時開示は契約追加後に
Providerを差し替えて有効化する。

### ロング中心の投資検討区分

```text
購入候補
  上向き完成パターン
  かつ ブレイク後5営業日以内で、勢い弱化・失敗・目標到達ではない
  かつ pattern_fit_score >= 65
  かつ volume_ratio >= 1.5
  かつ breakout_atr >= 0.1
  かつ |gap_atr| <= 1.5

様子見
  完成パターンなし、方向競合、出来高不足、ブレイク幅不足、ギャップ主導、
  保有監視期間、目標到達、または期限切れ

新規購入回避
  下向き完成パターン、上向きパターンの勢い弱化・失敗、
  またはパターンがなくても下落要因が優勢
```

下降パターンは新規購入・買い増しを止めて再確認する警戒フラグであり、空売りの実行指示には
使用しない。購入候補も自動発注条件ではない。自動取引へ進む際は、市場・業種・イベント評価、
リスク上限、取引コスト、ペーパートレードを別の必須ゲートとする。

初学者向けの計算式、状態遷移、研究根拠は`docs/investment-judgment-guide.md`に記載する。

### 交換可能性

`PatternDetector`と`AnalysisEngine`はProtocolで分離する。画面と候補一覧は共通の
`AnalysisResult`だけを参照し、パターン検出器や分析エンジンを将来の統計モデル・機械学習
モデルへ置換してもWeb APIの契約を維持する。

## 主要データ

### daily_bars

日足OHLCVを取得元単位で保持する。

```text
symbol, trade_date, open, high, low, close,
volume, provider, is_adjusted, retrieved_at
```

### pipeline_runs / pipeline_run_items

```text
pipeline_runs(
  id, pipeline_name, status, started_at, finished_at, summary_json
)
pipeline_run_items(
  run_id, symbol, provider, status, received_count, upserted_count,
  first_date, last_date, error_message, analysis_json
)
```

`analysis_json`は1、5、20営業日ごとに、テクニカル方向、投資検討区分、根拠の強さ、
完成パターン、分析エンジン版を保存する。価格更新がない日も保存済み日足で再分析し、
日次処理時点の判断を実行履歴へ残す。

### watchlists / watchlist_items

初期分析対象を明示的に限定する。

```text
watchlists(id, name, created_at, updated_at)
watchlist_items(
  watchlist_id, symbol, provider, display_name,
  exchange, currency, sort_order, added_at
)
```

### watchlist_registrations

## マルチホライズン予測

```text
1営業日    エントリー時機と翌営業日のリスク
5営業日    主な候補抽出と想定保有期間
20営業日   中期相場環境とポジション抑制
```

複数期間の結果を単純多数決しない。5営業日で候補を選び、1営業日でエントリーを遅らせ、
20営業日でポジションを縮小・拒否する入力として使用する。

将来は分類確率に加えて次を推定する。

```text
expected_return
return_quantile_10
return_quantile_50
return_quantile_90
probability_loss_exceeds_limit
```

## 候補条件

- 承認済みモデルである。
- 確率校正済みである。
- 最新日足、特徴量、予測の基準日が一致する。
- 必要な履歴件数を満たす。
- 重大なデータ品質エラーがない。
- 勝ち分類の確率が設定閾値以上である。

初期順位は次で計算する。

```text
rank_score = 勝ち分類の確率 - 検証期間の基礎発生率
```

## 自動取引への拡張

画面表示処理から直接注文しない。予測、戦略判断、リスク検査、注文、約定照合を分離する。

```text
予測
  -> 戦略判断
  -> ポートフォリオ・リスク検査
  -> 注文意図
  -> 実行ワーカー
  -> 証券会社API
  -> 約定・残高照合
  -> 監査履歴
```

注文判断では確率だけでなく取引コスト控除後の期待収益を使う。

```text
期待純収益
  = 予測期待収益
  - 手数料
  - スプレッド
  - スリッページ
  - 保有コスト
```

必須の安全対策:

- 初期値無効の全体取引スイッチ
- 実取引前のペーパートレード
- 最大注文、最大ポジション、最大エクスポージャー
- 日次損失・ドローダウン停止
- 古い価格・予測の拒否
- 冪等キーによる重複注文防止
- 市場営業日と取引時間の確認
- 新規注文前の注文・残高照合
- 無人運転前の手動承認段階
- 判断、注文、約定、介入の追記専用監査履歴

証券会社の認証情報は実行ワーカーのみ保持し、Web画面、予測処理、特徴量処理から隔離する。
