# TOMOSHIBIYORI 製品・設計仕様

「日足から、明日の判断に小さな灯を。」をコンセプトとする。将来を断定するアプリではなく、
不確実な相場に対する日々の判断材料を、根拠と注意事項を添えて提示する。

画面のNext.js移行、本人認証、BFF、Docker内のサービス境界および外部公開前チェックは、
[フロントエンド・認証・実行環境設計](frontend-auth-architecture.md)に記載する。本書は投資判断機能と
データ処理の製品仕様に集中する。利用者向け画面はNext.jsへ統一し、FastAPIはJSON APIとする。

## 前提

- 個人利用のPC中心Webアプリケーションとする。
- スマートフォンは閲覧のみ対応する。
- 保有銘柄とウォッチリストは別の目的・データとして管理する。
- 分析候補はウォッチリスト内と、流動性上位の市場全体を切り替える。
- 日足の終値確定後に日次更新する。
- 通常画面の分析期間は5、20営業日とする。1営業日は互換APIだけに残す。
- 初期分析は機械学習を使わないルールベースとする。
- テクニカル方向は上昇、停滞、下落の3種類とする。
- ロング中心の投資検討区分は購入候補、様子見、新規購入回避とする。
- 5営業日をスイング候補ランキングの標準とし、20営業日は中長期の買い場確認に使う。
- 市場データ取得元はAlpha VantageとJ-Quantsを交換可能にする。
- J-Quantsの初期契約はLightプランとする。
- 予測は分析情報であり、注文指示とは分離する。

## 利用者の操作

### 候補確認

1. 日次処理完了後にダッシュボードを開く。
2. 購入候補、様子見、新規購入回避を切り替える。
3. 候補銘柄の根拠の強さ、価格、基準日を確認する。
4. 銘柄を選び、日足と判断材料を確認する。
5. スイング（5営業日先）と中長期の買い場（20営業日先）を切り替える。

### 銘柄確認

1. ウォッチリストから銘柄を選択する。
2. 1か月、3か月、6か月、1年、全期間から表示期間を選択する。
3. 必要に応じて開始日と終了日を直接指定する。
4. ローソク足、出来高、取得元、調整有無を確認する。
5. 総合判定、判定要因、分析方式の版、基準日を確認する。

### 過去当てはめ実績レポート

- ダッシュボードへ追加せず、証券コードと判定期間を指定する一回実行型CLIとする。
- 期間内の各取引日について、スイング5日と中長期20日の結果を同時に再構築する。
- 当時のテクニカル方向、投資検討区分、実績方向、実績日、一致・不一致、騰落率、ATR換算値を並べる。
- スタイル別に検証件数、方向一致件数、方向一致率、実績方向の内訳を集計する。
- 必要履歴または将来実績が不足する判定日は詳細から除外し、除外件数を表示する。
- 方向一致率は過去当てはめの3分類一致割合であり、売買勝率や将来性能とは表現しない。
- HTMLはCSSを内包し、外部通信なしでPC・スマートフォン・印刷から閲覧できるようにする。

### 銘柄登録

1. 日次バッチがJ-Quantsの全上場銘柄マスタをローカルDBへ同期する。
2. Web画面で4文字の証券コードを最大200件まとめて入力する。
3. 同期済みマスタへ一致するコードは、その場で正式名称付きのウォッチリストへ追加する。
4. 一致したコードは、外部APIを呼ばず、PostgreSQLに保存済みの日足からその場で分析して選択表示する。
5. マスタ未同期または不一致のコードだけを「確認待ち」とする。
6. 次回の日次バッチで再照合し、不一致の場合は理由付きの「登録失敗」として表示する。

### 保有銘柄

1. 同期済み銘柄マスタから証券コード、数量、平均取得単価を登録する。
2. 保有銘柄はウォッチリストへ暗黙に追加せず、独立して管理する。
3. 評価表示にはリアルタイム価格ではなく、最新の日足終値を使う。
4. 日次バッチの取得対象は、保有銘柄とウォッチリストの和集合とする。

### 銘柄削除

1. ウォッチリスト行の「削除」を選択する。
2. 証券コードと銘柄名を含む確認を表示する。
3. 確認後、`watchlist_items`と対応する登録状態だけを削除する。
4. `daily_bars`とバッチ実行履歴は削除せず、再登録時の再利用と監査に残す。
5. 削除後は画面を再読み込みし、残った先頭銘柄を選択する。

## UI/UX原則

- PCでは画面全体をアプリシェルとして固定し、銘柄一覧と詳細をそれぞれ内部スクロールにする。
- PCでは銘柄ナビゲーションを折りたたみ、チャートと判断材料へ表示幅を譲れるようにする。
- 狭い画面では銘柄ナビゲーションと詳細領域を縦に並べる。
- スイング／中長期は銘柄分類ではなく選択銘柄へ適用する分析条件なので、サイドバーではなく
  銘柄ヘッダー内の「分析スタイル」として切り替える。分析候補タブでは候補母集団を選ぶ条件にも
  なるため、同じ状態へ連動する切り替えをサイドバー内にも表示する。
- 判定要因は3列のカードで一覧し、画面幅に応じて2列、1列へ切り替える。
- 方向を色だけで表現せず、「上昇」「下落」と文字でも表示する。
- 上昇、停滞、下落の3判定スコアを常にまとめて表示する。
- データ基準日、取得元、調整有無、予測期間を表示する。
- 古いデータ、未取得、取得失敗を区別する。
- 未校正・未承認モデルの確率を候補一覧へ表示しない。
- ルールの判定スコアを予測確率と表現しない。
- 総合判定とともに支持要因、反対要因、停滞要因を表示する。
- 投資検討区分とテクニカル方向を混同せず、両方を表示する。
- パターン一致度、出来高倍率、ブレイク幅、窓開けを表示する。
- データ同期待ち、契約プラン対象外、アドオン未契約、評価不能を区別する。
- 利用できない確認項目は中立値にせず、判定の加点・減点から除外する。
- 期間選択は銘柄を切り替えても維持する。
- 営業日数だけでなく、想定利用期間、見る指標、企業価値を含まない注意を常に表示する。
- 無効化水準が計算できる場合、許容損失額から理論上限株数と100株単位の上限を表示する。
- 相対力とベータは、TOPIXとの共通取引日が不足する場合に推測せず「同期待ち」と表示する。

## サービス構成

初期段階は運用負担を抑えるため、モジュラーモノリスとする。

```text
ブラウザ
  -> Next.js
       -> 本人セッション確認
       -> BFF
            -> Bearer認証付きFastAPI JSON API
                 -> ダッシュボード照会
                 -> 日足・分析・AI照会
                 -> PostgreSQL

Docker日次バッチ
  -> MarketDataProvider
  -> Light参照データ（TOPIX、決算予定日）同期
  -> J-Quants全上場銘柄マスタ
  -> J-Quantsバルク日足（全市場）
  -> 登録待ち証券コードの銘柄マスタ照合
  -> 正規化・品質検査
  -> 日足保存
       -> ルールベース分析
  -> 予測保存
  -> 候補ランキング
  -> Slack通知
```

画面表示中に外部市場データAPIを呼ばない。画面は保存済みデータのみ参照し、速度、
再現性、API制限、障害分離を確保する。

`HistoricalValidationService`は銘柄とTOPIXの日足を一度だけ読み込み、各判定日について分析入力と
判定日後の実績へ分離する。分析エンジンを先に実行し、実績日足はその入力へ渡さない。判定日時点を
鮮度評価上の現在日として扱い、過去日足を「古いデータ」と誤判定しない。過去時点の決算予定
スナップショットがない間は`earnings_synced=False`として、後知恵による未来情報混入を防ぐ。

レポート生成はDBへ結果を保存しない読み取り専用処理とする。将来の正式なウォークフォワード検証は、
エンジン版、母集団、全判定時点、取引コストを事前固定して別サービス・別テーブルへ保存する。

FastAPI APIとバッチは同じDockerイメージとドメインコードを使うが、実行プロセスと環境変数を
分離する。市場データAPIキーとSlack Webhookは`batch`および手動CLI用の`app`だけへ渡し、
`api`と`frontend`には渡さない。

OpenAI APIキーはAI最終確認を同期実行する`api`だけへ渡し、市場データAPIキーとは分離する。
ブラウザーへAPIキーを渡さず、FastAPIからResponses APIを呼ぶ。画面表示や銘柄選択では
自動実行せず、利用者の明示的なボタン操作を1回の実行単位とする。モデル名と出力上限も
`OPENAI_MODEL`、`OPENAI_MAX_OUTPUT_TOKENS`として`api`コンテナだけへ渡す。

## 日次バッチの実行契約

日次バッチは常駐プロセスではなく、一回実行して終了するジョブとする。外部スケジューラーが
`docker compose run --rm batch`を起動する。

1. PostgreSQL Advisory Lockを取得する。
2. `pipeline_runs`へ`running`状態を記録する。
3. J-QuantsのTOPIXと決算予定日を同期する。
4. 全上場銘柄マスタを単一トランザクションで更新する。
5. 全市場の日足は直近14暦日（おおむね10営業日）を毎回重複取得してUPSERTし、
   それより新しい未取得日も追加する。
6. 登録待ち証券コードを銘柄マスタで照合し、ウォッチリストへ昇格する。
7. 保有銘柄とウォッチリストの和集合を取得し、取得元ごとにProviderを再利用する。
8. OHLCVを検証してUPSERTする。
9. 対象銘柄を5、20営業日で分析し、市場全体の流動性上位銘柄を5営業日で分析する。
10. 参照データ、銘柄、市場スクリーニングの結果を実行履歴へ記録する。
11. 全体状態を`success`、`partial_failure`、`failed`のいずれかで確定する。
12. Advisory Lockを解放して終了する。

銘柄単位の認証、通信、レート上限、データ不正はその銘柄の失敗として隔離する。一部失敗時も
成功銘柄は確定し、再実行時は保存済み状態から再開する。直近期間の重複UPSERTにより取引所の
遡及訂正を反映し、調整係数が1以外となった銘柄は取得可能な全履歴を再取得する。想定外の全体障害も実行履歴を
`failed`へ更新してから再送出する。

過去5年の初期投入は日次バッチのAdvisory Lock内で実行しない。進捗、ファイル単位の成功状態、
レジューム機能を持つ`jquants-bulk-bootstrap`という独立CLIで実行する。日次バッチは初期投入の
未完了を検出した場合、無理に全履歴を処理せず再開コマンドを案内する。

## モジュール

```text
domain/          共通データ型
providers/       市場データ取得元
persistence/     SQLAlchemyスキーマ、接続、Alembic、旧SQLite移行
database.py      PostgreSQLリポジトリ関数
analysis/        共通分析契約、ルール、分析エンジン、過去当てはめ検証サービス
features/        版管理された特徴量計算
prediction/      学習、推論、確率校正
ranking/         候補条件と順位
web/             FastAPI JSON API、サービス間認証
frontend/        Next.js画面、Auth.js本人認証、BFF
charts/          チャート生成
```

### J-Quants Lightプラン

- V2 APIの`x-api-key`認証を使用する。
- 調整済みOHLCVを保存し、`is_adjusted`を真とする。
- `JQUANTS_PLAN=light`を既定とする。
- 60リクエスト/分を安全に下回るよう、リクエスト間隔を1.05秒以上に制御する。
- 初期取得範囲はバルクAPIで現在日から過去5年分とする。
- 初期取得は日次バッチと分離した、進捗保存・再開可能な専用CLIで行う。
- プラン年数ごとのバックフィル完了を記録し、Freeからの移行時も最初の一回だけ5年分を取得する。
- APIのページネーションへ追従する。
- 401・403、429、通信障害、データ形式不正を別のエラーとして扱う。
- TOPIX四本値と決算発表予定日を日次バッチで同期する。
- TOPIX以外の指数はLight対象外として非活性表示する。
- TDnet／適時開示はアドオン未契約として非活性表示する。

全市場の日足は分析母集団として保存するが、日足の存在を理由にウォッチリストへ自動追加しない。
登録申請は`watchlist_registrations`、有効なリストと構成銘柄は`watchlists`、
`watchlist_items`へ保存する。保有は`portfolios`、`positions`へ分離し、目的の異なる一覧を
混在させない。既定の異業種10銘柄投入は互換用の任意コマンドとして残す。

## データベース設計

- 開発環境はDocker Compose上のPostgreSQLを使用する。
- スキーマ変更はAlembicだけで適用し、Web起動時にテーブルを自動作成しない。
- 接続先は`DATABASE_URL`へ集約し、将来はAmazon RDS for PostgreSQLへ差し替える。
- 日足は`symbol`、`trade_date`、`provider`を一意キーとして冪等にUPSERTする。
- 銘柄マスタ更新は全件非活性化と最新データUPSERTを同じトランザクションで実行する。
- 非活性化された上場廃止銘柄のマスタ行と`daily_bars`は削除せず、時点を考慮する検証から参照できるよう保持する。
- バルクファイルごとの状態を保存し、失敗後の再実行で正常終了済みファイルを再取得しない。
- テストは開発DBと別の一時PostgreSQLを使う。
- 旧SQLiteは一度限りの移行元として読み取り専用でマウントし、確認完了まで削除しない。

## ルールベース分析

初版は次の独立したルールを集計する。

- スイングの5日・20日線、中長期の20日・60日線と長期線の傾き
- 分析期間に応じた価格モメンタム
- スイング14日・中長期28日RSIによる勢いと過熱感
- 実現ボラティリティと価格帯幅による停滞判定
- 出来高増加による値動きの確認
- 完成済みチャートパターン

各ルールは方向、重み、日本語の説明を返す。エンジンは重みを集計し、上昇要因と下落要因が
拮抗する場合は停滞とする。スコアは適用されたルールの重みを正規化した値であり、統計的に
校正された確率ではない。

スイングでは直近3営業日のATR換算変動と5日平均の位置を30点、中長期では直近10営業日と
20日平均の位置を26点で評価する。RSIの買われ過ぎ・
売られ過ぎは反転方向を直接予測せず、停滞側の警戒情報とする。パターンの保有監視期間、目標到達、
期限切れも現在方向へ加点しない。上向きパターンの勢い弱化・失敗は下落要因、下向きパターンの
勢い弱化・失敗は上昇要因へ切り替え、過去の形より直近価格を優先する。

```text
AnalysisService
  -> AnalysisEngine（共通契約）
       -> RuleBasedAnalysisEngine（現在）
            -> AnalysisRule群
       -> ModelAnalysisEngine（将来）
  -> AnalysisResult（共通出力）
```

画面と候補抽出は`AnalysisResult`だけに依存する。将来のモデル方式も同じ契約を実装し、
設定または依存性注入で切り替える。売買判断では分析方式と版を必ず記録する。

### 二層のチャート評価

パターンの形と、個別株固有の確認を分離する。

```text
TechnicalPatternDetector（価格形状）
  -> レクタングル
  -> アセンディング／ディセンディング・トライアングル
  -> ダブルトップ／ダブルボトム
  -> ヘッド＆ショルダーズ・トップ／ボトム

PatternLifecycleEvaluator（検出後の状態）
  -> 新規検討期間、保有監視期間
  -> 勢い弱化、目標到達、ブレイク失敗、期限切れ

TransitionReadinessEvaluator（転換前の進捗）
  -> 下降継続、底固め観察、転換準備、あと1条件
  -> 転換初動、上昇継続、警戒

PositionEntryEvaluator（中長期ポジションの押し目）
  -> 20日線・60日線の順序と60日線の傾き
  -> 20日線、60日線、直近20日安値、上抜け後の旧抵抗帯
  -> 支持候補への接触、終値維持、日足反発

LongOnlyDecisionPolicy（個別株向け投資検討区分）
  -> 出来高倍率
  -> ATRで標準化したブレイク幅と窓開け
  -> 最終日足のデータ鮮度
  -> 売買代金ベースの暫定流動性
  -> TOPIXトレンド、相対力、ベータ、業種指数、決算予定日、適時開示の評価可否
```

転換準備度は方向スコアや確率とは別の共通出力とする。必須条件の達成数、未達の次条件、転換水準、
無効化水準、参考目標、参考リスクリワードを保持する。市場全体の日次スナップショットにも段階と
進捗を保存し、「あと1条件」を後から検索できるようにする。評価器はProtocolで分離し、将来の
統計モデルへ交換しても`AnalysisResult`とWeb APIの契約を維持する。

中長期の押し目評価も`PositionEntryEvaluatorProtocol`で分離し、`AnalysisResult.position_entry`へ
格納する。20営業日分析だけで生成し、5営業日分析では`null`とする。支持候補は±0.35 ATRの帯、
接触後の参考無効化水準は帯下端-0.5 ATRとする。条件進捗は確率ではない。下降パターンが有効な
場合は押し目評価より下降警戒を優先し、決算直前5日、強いTOPIX下落、TOPIX比-5%未満では
購入候補を様子見へ落とす。

形の検出器は前日終値から当日終値へ水準を跨いだ日だけをイベントとして記録し、直近25営業日に
発生したイベントを返す。同じ水準の外側に留まっているだけの日を再検出しない。
`pattern_fit_score`は局所高値・安値、
回帰直線の傾き、左右対称性などの条件一致度を0〜100で表すヒューリスティックであり、
将来リターンの確率ではない。

検出後は価格形状とは分離した`PatternLifecycleEvaluator`が毎日再評価する。ブレイク後5営業日を
新規検討期間、6〜20営業日を保有監視期間、20営業日超を期限切れとする。直近最大4本が期待方向へ
0.5 ATR以上逆行した場合は勢い弱化とする。無効化水準は、上向きなら形成安値とネックラインの
0.5 ATR下の低い側から、さらに0.1 ATRの余裕を置く。形成値幅の目標到達も別状態にする。
ATRはWilder方式で平滑化する。閾値は固定した初期運用値であり、
日本株のウォークフォワード検証後にエンジン版を上げて変更する。

### 日足チャートの補助指標

日足APIは保存済みの調整済みOHLCVに加え、日付へ整列した補助指標を返す。スイングでは5日・
20日単純移動平均、Wilder RSI 14日、60営業日の抵抗帯候補、中長期では20日・60日単純移動平均、
Wilder RSI 28日、120営業日の抵抗帯候補を表示する。任意期間の開始日より前の日足を計算用の
助走期間に使い、表示期間だけをAPIレスポンスへ切り出す。将来データは使用しない。
中長期を選んだ場合は、`PositionEntryAssessment.supports`を青い帯としてチャートへ重ね、
抵抗帯とは色と名称を分ける。銘柄または運用スタイルを切り替えた直後は古い支持帯を消し、
新しい分析レスポンスを受け取ってから再描画する。

抵抗帯は、前後2本に対する局所高値を0.5 ATR以内で集約し、2接触以上、最低幅0.2 ATR、最大3件
とする。終値が上端を0.1 ATRより上抜けた帯は除く。表示用の抵抗帯検出は、投資判断用の
`TechnicalPatternDetector`と分離し、画面の表示切り替えで分析結果が変わらないようにする。
レスポンスの`score_is_probability`は`false`とし、抵抗帯が予測確率や確定価格でないことを明示する。

### AI最終確認

AI最終確認は、決定論的な`AnalysisResult`を変更せず、そのスナップショットを最新外部情報と照合する
別レイヤーとする。

```text
選択銘柄・運用スタイル
  -> AnalysisService（保存済み日足によるルールベース分析）
  -> OpenAIInvestmentReviewService
       -> Responses API
       -> web_search（公式IR・TDnet・取引所・報道）
  -> 本文、引用位置、情報取得日時
  -> Web画面で安全なテキストとクリック可能な引用へ変換
```

APIキー未設定時は機能状態を`not_configured`として返し、実行ボタンを非活性にする。実行時は
`store=false`とし、同一銘柄でも自動再利用せず、基準日・分析期間・モデル・調査日時を画面へ表示する。
一回の実行におけるWeb検索ツール呼び出しは最大6回へ制限する。
出力は日本語2,000文字程度を指示し、`OPENAI_MAX_OUTPUT_TOKENS`の既定値を6,000、許容範囲を
2,000〜20,000とする。APIが`status=incomplete`を返した場合は部分本文を破棄し、再実行または
上限変更を案内する。途中回答を投資判断として表示しない。
同一WebプロセスではAI調査を同時に1件だけ許可し、重複実行は`409`で拒否する。
AI本文を`innerHTML`へ渡さず、サーバーで検証した`http`または`https`の引用URLだけをDOMリンクへ
変換する。OpenAIのWeb検索で検索実行を確認できない回答は、最終確認結果として表示しない。

AIの参考区分は「検討継続」「保留」「新規購入見送り」とし、購入・売却・株数を直接指示しない。
ルールベースの判定スコアを確率へ変換せず、最新情報、テクニカルとの整合、反対材料、次の確認条件、
未確認事項を分ける。将来、自動取引へ接続するときもAI本文を直接注文条件にせず、検証済みの構造化
リスクゲートを別途必要とする。

### 個別株固有の特徴量

```text
volume_ratio   = ブレイク日出来高 / 過去60営業日出来高中央値
gap_atr        = (ブレイク日始値 - 前日終値) / ブレイク直前ATR(20)
breakout_atr   = ブレイク水準から終値までの方向別距離 / ブレイク直前ATR(20)
prior_trend_score = 形成前20日内の前後5日平均騰落率 × 500（-100〜100へ制限）
liquidity_score = J-Quants日本株の過去60営業日売買代金中央値による暫定評価
relative_strength = 対象株の20日または60日騰落率 - TOPIXの同期間騰落率
beta_topix = 共通取引日の日次騰落率から計算する対TOPIX単回帰ベータ
```

取得履歴が60営業日に満たない場合、`volume_ratio`と`liquidity_score`は20営業日以上の
取得可能期間を使い、その事実を画面に表示する。`|gap_atr| > 1.5`はギャップ主導として
通常ブレイクと区別する。決算予定日は取得するが決算内容や適時開示本文は取得しないため、
ギャップの原因を推測しない。

売買代金の閾値はJPY前提なので、現時点ではJ-Quants日本株だけに適用する。Alpha Vantageなど
日足自体に通貨情報を持たない取得元は流動性を評価不能とし、異なる通貨を同じ閾値で比較しない。

最新日足が現在日から7暦日を超えて古い場合、上向き条件を満たしても購入候補にはせず、
更新後の再確認を求める。下降パターンの新規購入回避は保守的な警戒情報として維持する。

TOPIXはLightの四本値からスイングでは20営業日、中長期では60営業日の騰落率、相対力、ベータを
算出する。相対力が-3%未満なら注意を追加するが、現段階では単独の除外条件にしない。
決算予定日は5日以内だけ購入候補を「様子見」へ抑制し、6日後から分析期間内までは警告だけを
表示する。同期前は`pending_data`、Light対象外の業種指数は
`plan_unavailable`、TDnetアドオン未契約は`addon_required`とし、0点として加算しない。
業種指数と適時開示は契約追加後にProviderを差し替えて有効化する。

転換準備は、転換水準の0.2 ATR下から0.1 ATR上、形成値幅0.5 ATR以上、出来高1.2倍以上を
使う。完成パターンの0.1 ATR上抜け・出来高1.5倍とは分離し、前者は様子見の早期発見、後者は
購入候補の確認に使う。

### ロング中心の投資検討区分

```text
購入候補
  上向き完成パターン
  かつ ブレイク後5営業日以内で、勢い弱化・失敗・目標到達ではない
  かつ pattern_fit_score >= 65
  かつ volume_ratio >= 1.5
  かつ breakout_atr >= 0.1
  かつ |gap_atr| <= 1.5
  かつ 20営業日分析では総合テクニカル方向が下落ではない

様子見
  転換初動、完成パターンなし、方向競合、出来高不足、ブレイク幅不足、ギャップ主導、
  保有監視期間、目標到達、または期限切れ

新規購入回避
  下向き完成パターン、上向きパターンの勢い弱化・失敗、
  またはパターンがなくても下落要因が優勢
```

下降パターンは新規購入・買い増しを止めて再確認する警戒フラグであり、空売りの実行指示には
使用しない。購入候補も自動発注条件ではない。自動取引へ進む際は、市場・業種・イベント評価、
リスク上限、取引コスト、ペーパートレードを別の必須ゲートとする。

株式投資の初学者向け基礎教材は`docs/technical-analysis-foundations.md`、実装の計算式、状態遷移、
研究根拠は`docs/investment-judgment-guide.md`に記載する。

モデルへ置換してもWeb APIの契約を維持する。

## 目的別の分析期間

```text
スイング（5営業日）       3・5・10・20日の値動きで転換初動と新規購入時機を確認
中長期の買い場（20営業日） 10・20・60日の値動きと支持帯反発で押し目を確認
```

営業日数は強制保有期間ではなく、参照窓と決算警戒範囲を決める。複数期間の結果を単純多数決せず、
5営業日はスイング候補抽出、20営業日は長期保有開始前の買い場確認として別々に読む。1営業日は
既存APIとの互換性だけに残し、通常画面、日次バッチ、候補ランキングでは使用しない。

将来は分類確率に加えて次を推定する。

```text
expected_return
return_quantile_10
return_quantile_50
return_quantile_90
probability_loss_exceeds_limit
```

## 候補条件

- 承認済みモデルである。
- 確率校正済みである。
- 最新日足、特徴量、予測の基準日が一致する。
- 必要な履歴件数を満たす。
- 重大なデータ品質エラーがない。
- 勝ち分類の確率が設定閾値以上である。

初期順位は次で計算する。

```text
rank_score = 勝ち分類の確率 - 検証期間の基礎発生率
```

## 自動取引への拡張

画面表示処理から直接注文しない。予測、戦略判断、リスク検査、注文、約定照合を分離する。

```text
予測
  -> 戦略判断
  -> ポートフォリオ・リスク検査
  -> 注文意図
  -> 実行ワーカー
  -> 証券会社API
  -> 約定・残高照合
  -> 監査履歴
```

注文判断では確率だけでなく取引コスト控除後の期待収益を使う。

```text
期待純収益
  = 予測期待収益
  - 手数料
  - スプレッド
  - スリッページ
  - 保有コスト
```

必須の安全対策:

- 初期値無効の全体取引スイッチ
- 実取引前のペーパートレード
- 最大注文、最大ポジション、最大エクスポージャー
- 日次損失・ドローダウン停止
- 古い価格・予測の拒否
- 冪等キーによる重複注文防止
- 市場営業日と取引時間の確認
- 新規注文前の注文・残高照合
- 無人運転前の手動承認段階
- 判断、注文、約定、介入の追記専用監査履歴

証券会社の認証情報は実行ワーカーのみ保持し、Web画面、予測処理、特徴量処理から隔離する。

## 実装段階

1. ウォッチリスト、期間指定日足、Web画面を実装する。
2. 取得元固有銘柄と標準銘柄識別子を分離する。
3. スイング5営業日と中長期20営業日の目的ラベルと特徴量を実装する。
4. ウォークフォワード検証、確率校正、モデル版管理を実装する。
5. 検証条件を満たしたモデルだけ候補表示する。
6. 日次処理とSlack通知を実装する。
7. 有料の東証データ取得元を追加する。
8. ペーパートレード、資産管理、リスク制限を実装する。
9. 注文・約定・照合を長期間検証する。
10. 手動承認と明示的な実取引フラグの背後に証券会社接続を追加する。

ウォークフォワード検証画面は、実績テーブルと時点別の検証処理が完成するまで架空の勝率を
表示しない。実装時はエンジン版、対象期間、件数、勝率、平均・中央値リターン、プロフィット
ファクター、最大ドローダウン、取引コスト前後を同じレポートに表示し、上場廃止銘柄を含む
母集団であるかも明記する。
